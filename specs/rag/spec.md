### User Story 1 - User asks a question and gets an answer (Priority: P1)

As a user, I want to ask a question in the chatbot interface and receive an answer that is relevant to the content of the textbook. The answer should be generated by an AI and should cite the sources from the textbook that were used to generate the answer.

**Why this priority**: This is the core functionality of the RAG chatbot and provides the primary value to the user. Without this, the feature is not usable.

**Independent Test**: This can be tested by inputting a question into the chatbot and verifying that an answer is returned and that the answer is relevant to the textbook content. The sources should also be verifiable.

**Acceptance Scenarios**:

1. **Given** the user is on a page with the RAG chatbot, **When** the user types a question into the chat input and submits, **Then** the chatbot should display a generated answer and the sources used to generate the answer.
2. **Given** the user has asked a question, **When** the chatbot is generating an answer, **Then** the chatbot should display a thinking or loading indicator.

---

### User Story 2 - System embeds textbook content (Priority: P1)

As a system administrator, I want the textbook content to be automatically processed, converted into embeddings, and stored in the vector database (Qdrant). This should happen whenever the textbook content is updated.

**Why this priority**: This is a high-priority task because the RAG chatbot cannot function without the textbook content being available in the vector database. This is a prerequisite for User Story 1.

**Independent Test**: This can be tested by adding or updating a chapter in the textbook, triggering the embedding process, and then verifying that the new content is present in the Qdrant vector database.

**Acceptance Scenarios**:

1. **Given** a new chapter is added to the textbook, **When** the embedding process is triggered, **Then** the content of the new chapter should be converted into embeddings and stored in the Qdrant vector database.
2. **Given** an existing chapter in the textbook is updated, **When** the embedding process is triggered, **Then** the updated content of the chapter should be converted into embeddings and the old embeddings should be updated or replaced in the Qdrant vector database.

---

### User Story 3 - User can see their chat history (Priority: P2)

As a user, I want to be able to see my previous questions and the answers I received from the chatbot. This will help me keep track of my conversation and refer back to previous answers.

**Why this priority**: This is a medium-priority task. While not essential for the core functionality, it significantly improves the user experience and makes the chatbot more useful.

**Independent Test**: This can be tested by asking multiple questions to the chatbot and verifying that the chat history is displayed correctly in the chatbot interface.

**Acceptance Scenarios**:

1. **Given** the user has asked one or more questions, **When** the user looks at the chatbot interface, **Then** the user should see a scrollable history of their questions and the chatbot's answers.
2. **Given** the chat history is long, **When** the user scrolls up, **Then** the user should be able to see older messages in the conversation.

### Edge Cases

- What happens when no relevant information is found in the textbook? The system should inform the user that it could not find relevant information and suggest rephrasing the question or asking a different one.
- How does the system handle offensive or inappropriate questions? The system should detect and flag such questions and refuse to answer them, possibly returning a canned response.
- What happens when the LLM fails to generate a coherent answer? The system should detect this (e.g., by checking for empty responses or specific error codes) and inform the user that it could not generate an answer.
- What happens when the Qdrant service is unavailable or returns an error? The system should gracefully handle the error, perhaps by logging it and informing the user about a temporary issue.
- What happens when the OpenAI service is unavailable or returns an error? Similar to Qdrant, the system should gracefully handle the error, log it, and inform the user.

### Functional Requirements

- **FR-001**: The system MUST allow users to input text queries for the RAG chatbot.
- **FR-002**: The system MUST display AI-generated answers to user queries based on textbook content.
- **FR-003**: The system MUST display the sources (e.g., chapter/section) from the textbook used to generate the answer.
- **FR-004**: The system MUST store and retrieve user chat history for the RAG chatbot.
- **FR-005**: The system MUST convert textbook content into vector embeddings using OpenAI's `text-embedding-3-small` model (vector_size=1536).
- **FR-006**: The system MUST store vector embeddings in Qdrant Cloud.
- **FR-007**: The system MUST perform semantic search in Qdrant to retrieve relevant content based on user queries.
- **FR-008**: The system MUST use an LLM (e.g., OpenAI GPT-4) to generate answers based on retrieved content and user queries.
- **FR-009**: The system MUST provide an endpoint (`/embeddings/upsert`) to trigger the embedding and upsert process for new or updated textbook content.
- **FR-010**: The system MUST provide an endpoint (`/rag/query`) to process user queries and return AI-generated answers with sources.
- **FR-011**: The system MUST detect and handle inappropriate user queries, refusing to answer and providing a predefined message.
- **FR-012**: The system MUST provide visual feedback (e.g., loading indicator) while processing user queries.

### Key Entities

- **User Query**: The text input from the user.
- **Textbook Content**: The raw text from the textbook chapters.
- **Embeddings**: Vector representations of the textbook content.
- **Qdrant Vector Database**: Stores the embeddings.
- **LLM Response**: The AI-generated answer to the user query.
- **Sources**: References to the parts of the textbook used to generate the answer.
- **Chat History**: A record of past user queries and LLM responses.

## Frontend Component: `RAGChatbot.tsx`

### Component Structure

The `RAGChatbot.tsx` component will be composed of the following key sub-components:

*   **Chat Input Area**: A dedicated text area for users to type their questions, accompanied by a clearly visible submit button.
*   **Chat History Display**: A scrollable container that sequentially shows past user questions and the corresponding AI-generated answers, including any cited sources.
*   **Loading Indicator**: A visual cue (e.g., spinner, progress bar) that appears when the system is processing a user query and generating a response.
*   **Error Message Display**: A designated area to present user-friendly error messages if any issues arise during the interaction.

### Interaction Flow

The interaction with the `RAGChatbot.tsx` component will follow this sequence:

1.  **User Input**: The user types a question into the text input area.
2.  **Submission**: The user clicks the submit button or presses the Enter key.
3.  **Input Clear**: The text in the input area is cleared immediately after submission.
4.  **Loading State**: A loading indicator becomes visible within the chat history display, signaling that the system is working on the request.
5.  **Backend Request**: The user's question is sent via an asynchronous request to the backend's `/rag/query` endpoint.
6.  **Response Processing**: The backend processes the query, performs RAG, and returns an AI-generated answer along with the relevant sources.
7.  **Loading State End**: The loading indicator disappears upon receiving the backend response.
8.  **Display Conversation**: The user's original question and the AI's generated answer (including sources) are appended to the chat history display, appearing in chronological order.
9.  **Error Handling**: If the backend returns an error, or if a network issue occurs, an appropriate and informative error message is displayed in the error message display area.

### Styling

The `RAGChatbot.tsx` component will adhere to the following styling guidelines:

*   **Docusaurus Integration**: The component's look and feel will seamlessly integrate with the existing Docusaurus theme of the textbook website.
*   **Clean and Intuitive**: The design will prioritize clarity and ease of use, ensuring an intuitive chat interface.
*   **Mobile-Friendly**: The component will be fully responsive and optimized for a positive user experience across various screen sizes and mobile devices.

## Backend Endpoints: FastAPI

### Endpoint: `/embeddings/upsert`

*   **HTTP Method**: `POST`
*   **Description**: Processes textbook content, converts it into vector embeddings using OpenAI, and upserts these embeddings into Qdrant. This endpoint is designed for administrative use or triggered by content updates.
*   **Request Body**:
    *   `content`: A string representing the textbook content to be embedded.
    *   `metadata`: (Optional) A dictionary containing metadata associated with the content (e.g., `chapter_title`, `section_id`, `url`).
*   **Success Response (200 OK)**:
    *   `status`: "success"
    *   `message`: "Embeddings upserted successfully."
    *   `upserted_count`: Number of vectors successfully upserted.
*   **Error Responses**:
    *   `400 Bad Request`: If `content` is missing or invalid.
    *   `500 Internal Server Error`: If there's an issue with OpenAI API, Qdrant connection, or embedding process.
*   **Interactions**:
    *   **OpenAI**: Uses `text-embedding-3-small` model to generate embeddings.
    *   **Qdrant**: Connects to Qdrant Cloud to store (upsert) the generated vectors and associated metadata.

### Endpoint: `/rag/query`

*   **HTTP Method**: `POST`
*   **Description**: Receives a user query, performs semantic search in Qdrant to retrieve relevant textbook content, and then uses an LLM (e.g., OpenAI GPT-4) to generate a coherent answer based on the query and retrieved content.
*   **Request Body**:
    *   `query`: A string representing the user's question.
    *   `user_id`: (Optional) A string identifier for the user, to potentially personalize responses or log interactions.
*   **Success Response (200 OK)**:
    *   `status`: "success"
    *   `answer`: A string containing the AI-generated answer.
    *   `sources`: An array of objects, each containing:
        *   `text`: The snippet of text from the textbook used as a source.
        *   `metadata`: Metadata associated with the source (e.g., `chapter_title`, `url`).
*   **Error Responses**:
    *   `400 Bad Request`: If `query` is missing or invalid.
    *   `403 Forbidden`: If an inappropriate query is detected.
    *   `500 Internal Server Error`: If there's an issue with OpenAI API, Qdrant connection, or LLM generation.
*   **Interactions**:
    *   **OpenAI**: Uses an LLM (e.g., GPT-4) to generate answers.
    *   **Qdrant**: Performs a semantic search to retrieve top-k most relevant vectors/documents based on the user's query embedding.

## Non-Functional Requirements

### Performance

*   **Latency**: User queries to the `/rag/query` endpoint should have a p95 latency of less than 5 seconds.
*   **Throughput**: The `/rag/query` endpoint should be able to handle at least 100 concurrent requests without significant degradation in latency.
*   **Embedding Speed**: The `/embeddings/upsert` process for an average-sized chapter should complete within 60 seconds.

### Reliability

*   **Uptime**: The RAG chatbot service (frontend and backend) should maintain a 99.9% uptime.
*   **Error Handling**: The system should gracefully handle errors from external services (OpenAI, Qdrant) and provide informative feedback to the user without crashing.
*   **Data Integrity**: Embeddings stored in Qdrant must accurately reflect the source textbook content.

### Security

*   **API Key Management**: OpenAI and Qdrant API keys must be securely stored and accessed (e.g., using environment variables or a secrets manager).
*   **Input Validation**: All input to backend endpoints must be validated to prevent injection attacks and other vulnerabilities.
*   **Access Control**: Access to the `/embeddings/upsert` endpoint should be restricted to authorized personnel or automated processes.
*   **Data Privacy**: User query data should be handled in accordance with privacy policies (e.g., anonymization, retention limits).

---

## Data Management

*   **Embedding Storage in Qdrant**:
    *   **Collection Name**: Embeddings will be stored in a dedicated Qdrant collection, e.g., `textbook_embeddings`.
    *   **Vector Size**: The vector size will be 1536, corresponding to OpenAI's `text-embedding-3-small` model.
    *   **Distance Metric**: Cosine similarity will be used for vector search.
    *   **Indexing**: Appropriate indexing strategies (e.g., HNSW) will be employed for efficient nearest neighbor search.
*   **Document Schema (Payload in Qdrant)**:
    *   Each point in Qdrant will store the embedding vector and a payload containing metadata about the original text.
    *   **`text`**: (string) The original text chunk that was embedded.
    *   **`chapter_title`**: (string) The title of the chapter the text belongs to.
    *   **`section_id`**: (string, optional) An identifier for the specific section within the chapter.
    *   **`url`**: (string, optional) The URL to the Docusaurus page where the content can be found.
    *   **`last_modified`**: (timestamp) The timestamp of the last modification of the content, useful for re-embedding logic.
*   **Data Consistency**:
    *   A mechanism will be in place to ensure that Qdrant embeddings are consistent with the latest version of the textbook content. This could involve periodic re-embedding or event-driven updates.
*   **Data Retention**:
    *   Policies for retaining or deleting old embeddings (e.g., when a chapter is removed) will be defined.
